# sf-monitor

Monitors SecuredFinance's on-chain smart contracts for critical safety events, alerting the team when they fire.

## What this is

A config-driven deployment of [OpenZeppelin Monitor](https://github.com/OpenZeppelin/openzeppelin-monitor) (`openzeppelin/openzeppelin-monitor` Docker image). We don't fork or build the monitor itself — we only author JSON config that tells it which networks/contracts/events to watch and where to send alerts. Runs via `docker-compose.yml` locally, or as a GKE deployment built from `Dockerfile` (see `.github/workflows/monitor-gke-deploy.yml`).

## Status

Migrated off OpenZeppelin Defender (Sentinel + Autotasks, deprecated) onto this self-hosted setup. The previous Defender-based TypeScript deployment code (`old-definitions/`) has been removed now that the concerns it covered are ported.

- **LendingMarketController liquidations/auto-rolls/itayose/block-unit-price, and TokenVault total-deposits: live**, generated (not hand-written) by `npm run generate` (`tools/generate-monitors.ts`), one concern module per condition under `tools/concerns/`. Set `SF_ENV` to `development`, `staging`, or `production` in `.env` and run it — it resolves that environment's contract addresses per chain dynamically from the private `@secured-finance/contracts` npm package (`tools/deployments.ts`) and writes `config/monitors/<network>-<concern>.json`. Only one environment's monitors exist on disk/deployed at a time (`npm run pregenerate` wipes the previous set first) — these generated files are gitignored, not committed; regenerate per environment instead.
- **Itayose and block-unit-price watch the wrong contract by default — fixed via live per-currency address resolution.** `BlockUnitPriceHistoryUpdated` and `ItayoseExecuted` are declared in `OrderActionLogic.sol`/`OrderBookLogic.sol`, but both are `delegatecall`'d from a per-currency `LendingMarket` beacon proxy, not `LendingMarketController` — confirmed directly with the Solidity team, and confirmed live on-chain (a matched transaction's event address was the proxy, not the Controller). A `delegatecall`'d library's log always carries the caller's address, never the library's own — pointing a monitor at `LendingMarketController` for these two events means it never matches anything. `tools/concerns/block-unit-price.ts` and `itayose.ts` both use the shared `resolveAddresses` hook in `tools/concerns/lending-market-addresses.ts`: at generate time, it calls `CurrencyController.getCurrencies()` then `LendingMarketController.getLendingMarket(ccy)` per currency (live via RPC, not `LendingMarketController.getUsedCurrencies()` — that's per-user and mutable, not a market registry), producing one monitored address per currency with an initialized market (currencies whose `getLendingMarket` returns the zero address — not yet initialized — are filtered out). `LiquidationExecuted`/`OrderBooksRotated` (the `liquidations`/`auto-rolls` concerns) were verified to genuinely emit from `LendingMarketController` itself, so they're untouched. **Known gap, deliberately deferred**: `CurrencyController.removeCurrency()` can de-list a currency from `getCurrencies()` without clearing its `LendingMarket` proxy mapping in `LendingMarketController` — a de-listed-but-still-live market could silently stop being watched on the next regenerate.
- **The generator now needs live RPC access, not just the private npm package.** `resolveAddresses` (above) requires an RPC connection per chain at generate time — new for this repo. Locally, `npm run generate` loads `.env` itself now (via `dotenv`, see `tools/generate-monitors.ts`) to get the RPC URL env vars named in `config/networks/*.json` (`tools/rpc.ts`). In the Docker build (`Dockerfile`'s `generator` stage), all four RPC URLs are passed as BuildKit `--secret` mounts alongside `NPM_AUTH_TOKEN` — never baked into an image layer — sourced in CI from the same GitHub secrets already used to create the runtime Kubernetes Secret (`.github/workflows/monitor-gke-deploy.yml`).
- **Total-deposits (large-withdrawal alert logic): live.** `tools/concerns/total-deposits.ts` watches TokenVault's `Withdraw` event directly (its own address, no `resolveAddresses` needed) and fires the `sf_monitor_total_deposits_check` script trigger (`config/triggers/scripts.json` → `config/triggers/scripts/total_deposits_check.py`), which resolves the withdrawn currency's token address live via `TokenVault.getTokenAddress` (web3.py, installed via this repo's `Dockerfile`) rather than a static currency→address map — deliberately kept live per-match rather than cached at generate time, since a stale cached token address would make the balance-movement math silently wrong rather than just visibly stop matching. Its alert text comes from `sf_alerts` like every other concern now, and it reports the withdrawn amount and the remaining vault balance in token decimals. Still open: no test validating the real OZ Monitor match-payload schema against the script's parsing.
- **Block-unit-price fluctuation *alert logic* (as opposed to the address-resolution fix above): live, ported from the old Defender Autotask with minimal changes.** Fires the `sf_monitor_block_unit_price_check` script trigger (`config/triggers/scripts.json` → `config/triggers/scripts/block_unit_price_check.py`), which keeps a rolling 5-entry price history per (network, currency, maturity) market as a JSON file under `data/block_unit_price_history/<network_slug>_<CURRENCY>_<maturity>.json` (the old Defender KV store's replacement — network is part of the key since the same currency can have a market at the same maturity timestamp on multiple networks independently) and alerts on any nonzero change across that window — same condition as the old handler, not a real fluctuation threshold. Still open: no real threshold (to be revisited with the team), and no test validating the real OZ Monitor match-payload schema against the script's parsing.
- **Itayose alert logic: live**, via the shared `event_alert.py` script trigger (`sf_monitor_itayose_alert`) — no custom state or threshold needed, only the address resolution above and the formatting below were the issues.
- **Every alert is now formatted and sent by a Python script trigger — there are no declarative Slack triggers left (`config/triggers/slack.json` is deleted).** Upstream's notification templating is plain `${events.0.args.x}` substitution over the decoded log, so a declarative trigger can only ever print the raw arg: a currency as 64 hex characters, a maturity as a Unix timestamp, an amount in base units, and a bare tx hash. That made liquidations/auto-rolls/itayose unreadable next to the two script-driven alerts, and no amount of config could fix it. So all five concerns fire script triggers, all alerts render through `config/triggers/scripts/sf_alerts.py`, and they share one shape: `[<SF_ENV>:<network>] <Title>`, an optional one-line summary, `Key: value` lines, and a `Tx:` explorer link last. `sf_alerts` also owns the value formatting — bytes32 → ticker, maturity → UTC date, unit price → percent of par (integers out of `Constants.PRICE_DIGIT` = 10000), amount → token decimals, addresses/tx hashes → explorer links.
  - Liquidations, auto-rolls and itayose need no logic beyond that formatting, so they share one script (`config/triggers/scripts/event_alert.py`) with a per-concern field list; which concern is being rendered arrives as the trigger's configured `arguments` (`config/triggers/scripts.json`), which upstream delivers as `args` on stdin — verified in the pinned source (`TriggerTypeConfig::Script.arguments` → `ScriptNotifier` → `executor.rs`). The alert conditions themselves stay entirely in each monitor's `match_conditions` — these scripts never decide *whether* to alert, only how it reads.
  - **Amounts are scaled by live token decimals, and `CurrencyController.getDecimals` is the wrong source for them** — it returns the *price feed's* aggregated decimals, not the token's (`decimalsCaches`, see the Solidity). The only currency → ERC20 mapping is `TokenVault.getTokenAddress`, so `sf_alerts.TokenInfo` resolves that and then `ERC20.decimals()`, live per match, cached for the life of the process. Decimals that can't be resolved render the amount as explicitly raw base units rather than assuming 18 — guessing would under-report a 6-decimal USDFC amount by 10^12 and make a real alert read as a non-event.
  - **The trigger scripts need contract addresses their own monitor doesn't watch**, since a liquidation/itayose match carries a `LendingMarketController` or `LendingMarket` proxy address but needs TokenVault to resolve decimals. The runtime image has no Node and no npm auth, so the generator writes the artifacts it already resolved to `config/triggers/scripts/contract_addresses.json` (gitignored, rewritten whole per `SF_ENV`, same lifecycle as `config/monitors/*.json`) — still no hand-typed addresses anywhere. If that file is missing or doesn't cover the matched network, amounts degrade to labelled raw base units rather than failing the alert.
  - Each script now also imports a shared module, which works because OZ Monitor runs a trigger as `python3 -c <file contents>` with cwd `/app`: `__file__` doesn't exist, so each script starts by putting `config/triggers/scripts` on `sys.path` and then `import sf_alerts`. Formatting is unit-tested (`tests/`, part of `npm test`) with no network, RPC or Slack — web3/requests are imported lazily inside the only functions that need them.
- **TokenVault large-withdrawal monitor (the old hand-written one): removed for now.** It previously lived at `config/monitors/ethereum_sepolia_tokenvault.json` (hand-written, not generated) but was deleted while restructuring around the generator — superseded by the total-deposits concern above, which covers the same contract via the generator instead.
- **Filecoin: live, and the only chain that needs a local RPC adapter.** `filecoin_mainnet` (chain 314, `filecoin-mainnet` stage) in production; `filecoin_calibration` (chain 314159) in development (`development-fil`) and staging (`staging-fil`). All five concerns generate for it unchanged — FIL and USDFC are the two currencies with initialized markets on mainnet (tFIL and USDFC on Calibration), so itayose/block-unit-price resolve to two addresses each.
  - **Why an adapter (`adapters/filecoin_adapter.py`) is unavoidable.** Filecoin has *null rounds* — epochs where no block was produced — and Lotus answers `eth_getBlockByNumber` for one with a hard JSON-RPC error (code 12), not an empty block. OZ Monitor's EVM client is a *dense* watcher: it requests every height in a range and collects them with `try_collect()`, so one failing height fails the whole batch, the watcher returns `Err` **without advancing the cursor**, and the next tick retries the identical range forever. Measured on mainnet, null rounds are ~1.25% of epochs (~36/day, bursty), so an unadapted monitor stalls permanently within ~40 minutes. Verified identical on GLIF, dRPC and Ankr — this is Lotus behaviour, not a provider quirk — and OZ Monitor's gap-tolerant `Sparse` stream kind is hardcoded unavailable to the EVM client (`get_blocks_with_meta`'s default impl always returns `Dense`). So the fix cannot be config-only, and cannot be a different provider.
  - **What the adapter does**, on loopback, read-only: translates a *confirmed* null round into an empty block so the cursor advances (an empty block matches no condition, so it can never invent an alert), and reports `eth_blockNumber` as finalized + 1, which `confirmation_blocks: 1` cancels back to exactly the finalized epoch. Everything else fails closed — method allowlist, upstream envelope/identity validation, and a staleness guard on the watermark. Null rounds are matched on the error *code*, not the message prose.
  - **`max_past_blocks: "unlimited"`** (unlike the other networks) so Filecoin never silently skips epochs after downtime; upstream's own validation recommends exactly this (`Use "unlimited" to never skip`), and catch-up is capped by the engine at `CATCHUP_BATCH_SIZE × MAX_BATCHES_PER_TICK` = 3,000 blocks/tick, so it is not an unbounded backfill.
  - **Alert latency is much higher than the other chains, and differs per network**: alerts can only be as fresh as Filecoin finality, measured at ~23 epochs (~12 min) on mainnet but ~196 epochs (~98 min) on Calibration. `FILECOIN_MAX_FINALIZED_AGE_SECONDS` must stay above that lag (1800 mainnet / 10800 Calibration) or the staleness guard rejects every watermark read and halts monitoring.
  - **The monitor container must not start before the adapter is serving — `adapters/wait_for_adapter.py` enforces this.** OZ Monitor builds its per-network watchers **once, at boot**, in a loop that merely logs on failure and moves on (`src/main.rs`: `if let Ok(client) = client_pool.get_evm_client(&network).await { ... } else { error!("Failed to get EVM client for network: {}", network.slug); }`). Nothing retries afterwards. Both containers start together, and the adapter verifies upstream before binding its port — so without the gate a slow adapter leaves Filecoin with **no watcher at all**, permanently, while the Pod stays `Running` and every probe passes. A readiness probe on the sidecar cannot prevent this: readiness gates Service endpoints, not a sibling container's startup. The gate exits non-zero if the adapter never answers, so the Pod crash-loops visibly instead of running half-blind.
  - **The empty-log check fails closed on missing evidence, not open.** `eth_getLogs` returning `[]` is only trusted when a *validated* header for that exact height says the block has no logs. If the fallback header request times out, errors, or comes back for the wrong height, the empty result is rejected rather than accepted — unavailable evidence is not evidence of absence. This is why `_maybe_null_round` records each synthesized epoch as empty: a null round has no header to fetch, so without that cache entry the stricter check would reject every legitimate null round and turn it into a stall.
  - **Docker Compose needs `entrypoint`, not `command`, for the adapter.** The upstream image's `ENTRYPOINT` is `/app/openzeppelin-monitor` and Compose *appends* `command` to it, so a command-only override runs the monitor binary with the script path as an argv and the adapter never starts. Kubernetes `command` replaces the entrypoint, which is why the GKE manifest overrides it there instead.
  - **Script-trigger `timeout_ms` had to rise from 5s to 20s because of Filecoin's RPC latency.** `total_deposits_check.py` makes four sequential `eth_call`s (token address, the balance at the matched block and at the one before it, and — since alerts began reporting amounts in token decimals — `ERC20.decimals()`) plus a Slack POST. Through Alchemy at ~50ms a call that fits in 5s easily; through GLIF at ~1s a call it does not — measured replays of two real Calibration withdrawals took 5.13s (just passed) and 6.07s (timed out). The failure is near-silent: the trigger logs `Script execution timed out` but OZ Monitor still logs `Successfully sent notifications for match` and exits 0, so a real large-withdrawal alert is simply never delivered. `block_unit_price_check.py` and the liquidation/auto-roll/itayose alerts make at most one or two calls (none at all for auto-rolls, which has no amount to scale), but all of them share the value.
  - **Known gap:** the staleness guard, a wedged adapter, and an unmatched null round all fail *closed* — correct for a safety monitor, but they stall silently. The sidecar's liveness probe restarts a wedged process and rejections are logged with their cause, but there is still no alert on "the monitor stopped monitoring"; cursor-lag alerting is the open follow-up.

## Layout

- `config/networks/` — RPC/chain definitions per network (`slug` must match what monitors reference in their `networks` array: `ethereum_mainnet`, `ethereum_sepolia`, `arbitrum_one`, `arbitrum_sepolia`, `filecoin_mainnet`, `filecoin_calibration`). The two Filecoin files point at `FILECOIN_ADAPTER_URL` (the loopback adapter), not at a Filecoin endpoint directly — see Status above.
- `config/monitors/` — one file per contract/event set being watched (address(es), ABI fragment, match conditions, which triggers to fire). Files matching `*-liquidations.json`/`*-autorolls.json`/`*-itayose.json`/`*-totaldeposits.json`/`*-blockunitprice.json` are generated (gitignored, see `tools/`) — everything else here is hand-written and committed.
- `config/filters/` — custom filter scripts, if any
- `config/triggers/` — alert destinations: `scripts.json` + `scripts/`, which is where every Slack alert now comes from (`sf_alerts.py` — shared formatting and delivery for all of them; `event_alert.py` — liquidations/auto-rolls/itayose, which need formatting only; `total_deposits_check.py` and `block_unit_price_check.py` — the two with their own logic/state; `network_explorers.json` — per-network block-explorer base URLs; `contract_addresses.json` — generated, see Status above), plus `log.json` (routes to `scripts/log_match.sh`, which appends every match to `logs/monitor-matches.log`). There is no `slack.json`: see Status above for why declarative Slack triggers couldn't produce a readable alert. `scripts/list_token_vault_balances.py` is a standalone diagnostic (not an OZ Monitor trigger) — run manually to sanity-check TokenVault balances per currency against the currently generated monitor set.
- `data/` — per-network last-processed-block cursor, plus `block_unit_price_history/<network_slug>_<CURRENCY>_<maturity>.json` (per-market rolling price history the block-unit-price script trigger reads/writes) (gitignored)
- `logs/` — monitor match logs (gitignored)
- `.env` — RPC URLs, `SLACK_WEBHOOK_URL`, `NPM_AUTH_TOKEN`, `SF_ENV` (gitignored; see `.env.example`). Needed both by the deployed monitor container and, now, by `npm run generate` itself (see Status above). Filecoin deliberately has several variables rather than one: `FILECOIN_MAINNET_RPC_URL`/`FILECOIN_CALIBRATION_RPC_URL` are the real upstreams the *generator* uses, `FILECOIN_UPSTREAM_RPC_URL` is the single endpoint the *adapter* bridges, and `FILECOIN_ADAPTER_URL` is the loopback address *OZ Monitor and the trigger scripts* talk to. Collapsing these into one name would mean the same variable holding an upstream URL at build time and a loopback URL at runtime.
- `adapters/` — `filecoin_adapter.py`, the loopback null-round bridge (see Status above), and `wait_for_adapter.py`, the startup gate the monitor container runs before `exec`ing the monitor binary, plus their tests (`npm test`, which also runs `tests/` — the alert-formatting tests; stdlib `unittest`, no network calls or sleeps — `bridge()` takes its upstream as an argument and `wait_for()` takes its sleep and opener). `npm test` runs in `.github/workflows/build.yml`. Not an OZ Monitor trigger script: it runs as its own process, a sidecar container in GKE and a `network_mode: service:monitor` service in `docker-compose.yml` so loopback is shared the same way in both.
- `tests/` — Python tests for the alert formatting (`config/triggers/scripts/sf_alerts.py`, `event_alert.py`), run by `npm test` alongside the `adapters/` tests. No network, RPC or Slack: the RPC and HTTP seams are substituted.
- `tools/` — the monitor generator (Node/TypeScript, `npm run generate`). `environments.ts` maps each `SF_ENV` to the chains/deploy-stages it covers; `deployments.ts` dynamically resolves each chain's contract addresses from the private `@secured-finance/contracts` npm package (auth via `NPM_AUTH_TOKEN`); `rpc.ts` builds a read-only viem client per network for concerns needing live RPC resolution; `types.ts` defines the `Concern` shape, including the optional `resolveAddresses` hook; `concerns/*.ts` define one watched condition each (event ABI, signature, trigger, optional `resolveAddresses`) — `concerns/lending-market-addresses.ts` is the shared resolver `block-unit-price.ts`/`itayose.ts` both use; `generate-monitors.ts` ties it all together and writes `config/monitors/` plus `config/triggers/scripts/contract_addresses.json` (the addresses the trigger scripts need at runtime — see Status above).
- `Dockerfile` — two-stage build: a `generator` stage runs `npm run generate` to bake one `SF_ENV`'s `config/monitors/*.json` into the image (a deployed container has no bind mount to fall back on the way `docker-compose` does), needing `NPM_AUTH_TOKEN` and all six RPC URLs as BuildKit `--secret` mounts; the final stage is the upstream `openzeppelin-monitor` image plus `pip install web3` (for the Python trigger scripts' RPC calls) and a copy of `adapters/`.
- `.github/workflows/monitor-gke-deploy.yml` — manual dispatch only (`environment` input: development/staging/production), no push trigger. Development/staging are for testing and are never deployed to GCP automatically; production deploys are equally deliberate, not tied to a merge. Builds and pushes the image for the chosen environment (passing the same secrets as the local Docker build), creates/replaces the runtime Kubernetes Secret (Slack webhook + all four EVM RPC URLs + the env-appropriate `FILECOIN_UPSTREAM_RPC_URL`), and rolls out the GKE deployment. The Pod runs two containers — the monitor and the Filecoin adapter sidecar — in **every** environment, not just production, so development/staging on Calibration exercise the identical code path before it reaches mainnet. The sidecar's probes are `exec`, not `httpGet`: the adapter binds `127.0.0.1`, which the kubelet cannot reach via the Pod IP.

## Working principles

- **Minimal code changes**, but not at the cost of hardcoding what has a real dynamic source. OZ Monitor's own config format is static (no env-var templating for contract addresses), but contract addresses/ABI fragments still come from the private `@secured-finance/contracts` package and, where needed, live RPC calls, dynamically via `tools/generate-monitors.ts` — never hand-type an address into a monitor JSON file if the generator can resolve it.
- Only one `SF_ENV` (development/staging/production) is ever deployed on a given monitor instance at a time — the generator reflects that: `npm run generate` regenerates and replaces the full monitor set for whichever `SF_ENV` is set, and those generated files are gitignored rather than committed.
- New watched conditions go in `tools/concerns/` (event ABI + signature + trigger), not as hand-written JSON — see `tools/concerns/liquidations.ts` for the simple pattern (a single static address), `tools/concerns/total-deposits.ts` for one whose trigger has its own logic, and `tools/concerns/block-unit-price.ts`/`itayose.ts` for ones needing `resolveAddresses` (multiple live-resolved addresses). A concern needing nothing but an alert should add a field list to `config/triggers/scripts/event_alert.py` and a trigger to `config/triggers/scripts.json` rather than a new script — and never a declarative Slack trigger, which can't format anything (see Status above). Hand-written monitor JSON is still the right approach for contracts/conditions the generator doesn't cover yet (nothing currently).
- **Verify which contract address actually emits an event before wiring a monitor to it — don't assume it's the contract you call into.** A library's event emitted via `delegatecall` always carries the *caller's* address in the log, not the library's own deployed address, and not necessarily the outermost contract a user's transaction was sent to either. `block-unit-price`/`itayose` both shipped originally pointed at `LendingMarketController` and would never have matched a single real event; this was only caught by testing live on-chain and confirming with the Solidity team. When possible, verify against the actual Solidity source (or a live test transaction) rather than by analogy to how another event/contract already in this repo behaves.
- **`adapters/` is the one deliberate exception to "config only, never build the monitor" — keep it that way.** We still don't fork OZ Monitor; the Filecoin adapter sits *outside* it as a loopback RPC bridge, because the null-round incompatibility is in the engine's EVM block-fetching path and is not reachable from config (verified against the pinned `v1.6.0` source, not inferred). Before adding another adapter, prove the same three things: that config can't express it, that no RPC provider behaves differently, and that no newer OZ Monitor release fixes it. A bridge that can only *delete* data (an empty block) is acceptable; one that invents data a monitor could alert on is not.
- **Verify claims about the engine against the pinned source, not against its docs or a summary.** `Dockerfile` pins `openzeppelin-monitor:v1.6.0`; the matching source is tag `v1.6.0` (commit `102b9ada`). Several plausible-sounding beliefs about this engine turned out to be wrong when checked — e.g. that a failed fetch advances the cursor (it does not: it returns `Err` and leaves it), and that `eth_call` fails at a Filecoin null round (it does not: Lotus resolves state to the nearest tipset, so only `eth_getBlockByNumber` needs translating). Read the Rust.
- Contract addresses and events being monitored are security-critical — changes here should be deliberate and reviewed, since a misconfigured monitor means missed alerts on real protocol risk.
- **Known pre-existing risk, unrelated to Filecoin but worth fixing next:** `ethereum_mainnet` (`max_past_blocks: 54`) and `arbitrum_one` (`750`) clamp their catch-up window, so an outage longer than roughly 11 minutes (Ethereum) or 3 minutes (Arbitrum) makes the watcher skip the gap entirely — it only *logs* `(skipped N blocks)`, it does not alert. `emptyDir` + `strategy: Recreate` compounds it: every deploy resets the cursor and jumps to head. Filecoin's `"unlimited"` is the pattern these two should adopt.
