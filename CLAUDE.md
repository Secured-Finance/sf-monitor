# sf-monitor

Monitors SecuredFinance's on-chain smart contracts for critical safety events, alerting the team when they fire.

## What this is

A config-driven deployment of [OpenZeppelin Monitor](https://github.com/OpenZeppelin/openzeppelin-monitor) (`openzeppelin/openzeppelin-monitor` Docker image). We don't fork or build the monitor itself — we only author JSON config that tells it which networks/contracts/events to watch and where to send alerts. Runs via `docker-compose.yml` locally, or as a GKE deployment built from `Dockerfile` (see `.github/workflows/monitor-gke-deploy.yml`).

## Status

Migrated off OpenZeppelin Defender (Sentinel + Autotasks, deprecated) onto this self-hosted setup. The previous Defender-based TypeScript deployment code (`old-definitions/`) has been removed now that the concerns it covered are ported.

- **LendingMarketController liquidations/auto-rolls/itayose/block-unit-price, and TokenVault total-deposits: live**, generated (not hand-written) by `npm run generate` (`tools/generate-monitors.ts`), one concern module per condition under `tools/concerns/`. Set `SF_ENV` to `development`, `staging`, or `production` in `.env` and run it — it resolves that environment's contract addresses per chain dynamically from the private `@secured-finance/contracts` npm package (`tools/deployments.ts`) and writes `config/monitors/<network>-<concern>.json`. Only one environment's monitors exist on disk/deployed at a time (`npm run pregenerate` wipes the previous set first) — these generated files are gitignored, not committed; regenerate per environment instead.
- **Itayose and block-unit-price watch the wrong contract by default — fixed via live per-currency address resolution.** `BlockUnitPriceHistoryUpdated` and `ItayoseExecuted` are declared in `OrderActionLogic.sol`/`OrderBookLogic.sol`, but both are `delegatecall`'d from a per-currency `LendingMarket` beacon proxy, not `LendingMarketController` — confirmed directly with the Solidity team, and confirmed live on-chain (a matched transaction's event address was the proxy, not the Controller). A `delegatecall`'d library's log always carries the caller's address, never the library's own — pointing a monitor at `LendingMarketController` for these two events means it never matches anything. `tools/concerns/block-unit-price.ts` and `itayose.ts` both use the shared `resolveAddresses` hook in `tools/concerns/lending-market-addresses.ts`: at generate time, it calls `CurrencyController.getCurrencies()` then `LendingMarketController.getLendingMarket(ccy)` per currency (live via RPC, not `LendingMarketController.getUsedCurrencies()` — that's per-user and mutable, not a market registry), producing one monitored address per currency with an initialized market (currencies whose `getLendingMarket` returns the zero address — not yet initialized — are filtered out). `LiquidationExecuted`/`OrderBooksRotated` (the `liquidations`/`auto-rolls` concerns) were verified to genuinely emit from `LendingMarketController` itself, so they're untouched. **Known gap, deliberately deferred**: `CurrencyController.removeCurrency()` can de-list a currency from `getCurrencies()` without clearing its `LendingMarket` proxy mapping in `LendingMarketController` — a de-listed-but-still-live market could silently stop being watched on the next regenerate.
- **The generator now needs live RPC access, not just the private npm package.** `resolveAddresses` (above) requires an RPC connection per chain at generate time — new for this repo. Locally, `npm run generate` loads `.env` itself now (via `dotenv`, see `tools/generate-monitors.ts`) to get the RPC URL env vars named in `config/networks/*.json` (`tools/rpc.ts`). In the Docker build (`Dockerfile`'s `generator` stage), all four RPC URLs are passed as BuildKit `--secret` mounts alongside `NPM_AUTH_TOKEN` — never baked into an image layer — sourced in CI from the same GitHub secrets already used to create the runtime Kubernetes Secret (`.github/workflows/monitor-gke-deploy.yml`).
- **Total-deposits (large-withdrawal alert logic): live.** `tools/concerns/total-deposits.ts` watches TokenVault's `Withdraw` event directly (its own address, no `resolveAddresses` needed) and fires the `sf_monitor_total_deposits_check` script trigger (`config/triggers/scripts.json` → `config/triggers/scripts/total_deposits_check.py`), which resolves the withdrawn currency's token address live via `TokenVault.getTokenAddress` (web3.py, installed via this repo's `Dockerfile`) rather than a static currency→address map — deliberately kept live per-match rather than cached at generate time, since a stale cached token address would make the balance-movement math silently wrong rather than just visibly stop matching. Still open: no test validating the real OZ Monitor match-payload schema against the script's parsing.
- **Block-unit-price fluctuation *alert logic* (as opposed to the address-resolution fix above): live, ported from the old Defender Autotask with minimal changes.** Fires the `sf_monitor_block_unit_price_check` script trigger (`config/triggers/scripts.json` → `config/triggers/scripts/block_unit_price_check.py`), which keeps a rolling 5-entry price history per (currency, maturity) market as a JSON file under `data/block_unit_price_history/<CURRENCY>_<maturity>.json` (the old Defender KV store's replacement) and alerts on any nonzero change across that window — same condition as the old handler, not a real fluctuation threshold. Still open: no real threshold (to be revisited with the team), and no test validating the real OZ Monitor match-payload schema against the script's parsing.
- **Itayose alert logic: live**, a plain declarative Slack trigger (`sf_monitor_slack_itayose` in `config/triggers/slack.json`) — no custom script/state needed, only the address resolution above was the issue.
- **TokenVault large-withdrawal monitor (the old hand-written one): removed for now.** It previously lived at `config/monitors/ethereum_sepolia_tokenvault.json` (hand-written, not generated) but was deleted while restructuring around the generator — superseded by the total-deposits concern above, which covers the same contract via the generator instead.
- Filecoin not yet configured.

## Layout

- `config/networks/` — RPC/chain definitions per network (`slug` must match what monitors reference in their `networks` array: `ethereum_mainnet`, `ethereum_sepolia`, `arbitrum_one`, `arbitrum_sepolia`)
- `config/monitors/` — one file per contract/event set being watched (address(es), ABI fragment, match conditions, which triggers to fire). Files matching `*-liquidations.json`/`*-autorolls.json`/`*-itayose.json`/`*-totaldeposits.json`/`*-blockunitprice.json` are generated (gitignored, see `tools/`) — everything else here is hand-written and committed.
- `config/filters/` — custom filter scripts, if any
- `config/triggers/` — alert destinations: `slack.json` (declarative Slack alerts, including the per-concern ones and an ad hoc `sf_monitor_slack` test trigger not wired to any generated concern), `log.json` (routes to `scripts/log_match.sh`, which appends every match to `logs/monitor-matches.log`), `scripts.json` + `scripts/` for monitors needing custom computation/state (`total_deposits_check.py`, `block_unit_price_check.py`, `network_explorers.json` — per-network block-explorer base URLs both scripts use for tx links). `scripts/list_token_vault_balances.py` is a standalone diagnostic (not an OZ Monitor trigger) — run manually to sanity-check TokenVault balances per currency against the currently generated monitor set.
- `data/` — per-network last-processed-block cursor, plus `block_unit_price_history/<CURRENCY>_<maturity>.json` (per-market rolling price history the block-unit-price script trigger reads/writes) (gitignored)
- `logs/` — monitor match logs (gitignored)
- `.env` — RPC URLs, `SLACK_WEBHOOK_URL`, `NPM_AUTH_TOKEN`, `SF_ENV` (gitignored; see `.env.example`). Needed both by the deployed monitor container and, now, by `npm run generate` itself (see Status above).
- `tools/` — the monitor generator (Node/TypeScript, `npm run generate`). `environments.ts` maps each `SF_ENV` to the chains/deploy-stages it covers; `deployments.ts` dynamically resolves each chain's contract addresses from the private `@secured-finance/contracts` npm package (auth via `NPM_AUTH_TOKEN`); `rpc.ts` builds a read-only viem client per network for concerns needing live RPC resolution; `types.ts` defines the `Concern` shape, including the optional `resolveAddresses` hook; `concerns/*.ts` define one watched condition each (event ABI, signature, trigger, optional `resolveAddresses`) — `concerns/lending-market-addresses.ts` is the shared resolver `block-unit-price.ts`/`itayose.ts` both use; `generate-monitors.ts` ties it all together and writes `config/monitors/`.
- `Dockerfile` — two-stage build: a `generator` stage runs `npm run generate` to bake one `SF_ENV`'s `config/monitors/*.json` into the image (a deployed container has no bind mount to fall back on the way `docker-compose` does), needing `NPM_AUTH_TOKEN` and all four RPC URLs as BuildKit `--secret` mounts; the final stage is the upstream `openzeppelin-monitor` image plus `pip install web3` (for the Python trigger scripts' RPC calls).
- `.github/workflows/monitor-gke-deploy.yml` — manual dispatch only (`environment` input: development/staging/production), no push trigger. Development/staging are for testing and are never deployed to GCP automatically; production deploys are equally deliberate, not tied to a merge. Builds and pushes the image for the chosen environment (passing the same secrets as the local Docker build), creates/replaces the runtime Kubernetes Secret (Slack webhook + all four RPC URLs), and rolls out the GKE deployment.

## Working principles

- **Minimal code changes**, but not at the cost of hardcoding what has a real dynamic source. OZ Monitor's own config format is static (no env-var templating for contract addresses), but contract addresses/ABI fragments still come from the private `@secured-finance/contracts` package and, where needed, live RPC calls, dynamically via `tools/generate-monitors.ts` — never hand-type an address into a monitor JSON file if the generator can resolve it.
- Only one `SF_ENV` (development/staging/production) is ever deployed on a given monitor instance at a time — the generator reflects that: `npm run generate` regenerates and replaces the full monitor set for whichever `SF_ENV` is set, and those generated files are gitignored rather than committed.
- New watched conditions go in `tools/concerns/` (event ABI + signature + trigger), not as hand-written JSON — see `tools/concerns/liquidations.ts` for a Slack-triggered pattern with a single static address, `tools/concerns/total-deposits.ts` for a script-triggered one, and `tools/concerns/block-unit-price.ts`/`itayose.ts` for ones needing `resolveAddresses` (multiple live-resolved addresses). Hand-written monitor JSON is still the right approach for contracts/conditions the generator doesn't cover yet (nothing currently).
- **Verify which contract address actually emits an event before wiring a monitor to it — don't assume it's the contract you call into.** A library's event emitted via `delegatecall` always carries the *caller's* address in the log, not the library's own deployed address, and not necessarily the outermost contract a user's transaction was sent to either. `block-unit-price`/`itayose` both shipped originally pointed at `LendingMarketController` and would never have matched a single real event; this was only caught by testing live on-chain and confirming with the Solidity team. When possible, verify against the actual Solidity source (or a live test transaction) rather than by analogy to how another event/contract already in this repo behaves.
- Contract addresses and events being monitored are security-critical — changes here should be deliberate and reviewed, since a misconfigured monitor means missed alerts on real protocol risk.
